RENDERING LAB実験と検証の記録

004 · 個別描画とインスタンシング

全条件・全 repeat で、両方式の 512×512 RGB readback が bit-exact 一致しました。

この run で instanced の total 中央値が individual 以上だった条件は、oblique/64、oblique/256 です。常に total が短縮するという結果ではありません。

実行環境は Mesa llvmpipe の CPU ソフトウェアラスタライザーで、backend は GL です。記録した時間は、ハードウェア GPU の timestamp やブラウザーのフレーム時間、Android 実機の性能ではありません。

目的と問い

静的な同一メッシュを個別に描く場合と、インスタンシングでまとめて描く場合を比較します。画像を保ちながら、描画コマンドの記録と処理全体の時間がどう変わるかを確認します。

比較条件

固定した条件

両方式では、シェーダー、メッシュ、instance buffer、カメラ、材質、深度、viewport を共通にしています。

adapter は llvmpipe (LLVM 19.1.7, 256 bits)、backend は Gl、device type は Cpu です。driver は (empty driver name returned by adapter API)、driver info は 4.5 (Core Profile) Mesa 25.0.7-2+deb13u1 です。

Rust のネイティブ実行には release profile（debug_assertions=false）と rustc 1.99.0 (b940084d7 2026-09-28) を使いました。release でも、ネイティブの driver・CPU・queue の構成は Web 版やハードウェア GPU と異なります。

表示・内部寸法はともに 512×512、倍率は 100%、時刻は t=0 です。Rgba8UnormSrgb color と Depth32Float を使い、depth compare は Less、深度書き込みは有効にします。back-face culling と Lambert shader は共通です。100% でも、共通の linear-light bilinear fullscreen display pass を含めます。

unit cube は 24 vertices・36 indices・12 triangles です。各 instance は translation、非一様 scale、color で構成し、vec4 × 3 ＝48 bytes です。位置は間隔 0.16 の整数座標による正方形のらせんで、幅は 0.11、高さは 0.16 または 0.40、色は固定の3色 palette を使います。N 個の条件では、先頭 N 件を使います。

変えた条件

同じ unit cube から作った静的な箱・柱を、個別の draw と1回の instanced draw で描きます。1・64・256・1024・4096個、2視点の計20条件で、各 3 repeat × 30 sample ＝1800点を記録しました。

oblique の eye は [8.2,6.8,10.5]、overhead の eye は [0.1,17,0.1]、target は [0,0.6,0] です。45° の透視投影で、near 0.1 / far 100 に設定します。overhead の微小な offset は、真上の特異点を避けるためのものです。

物体数を増やすと、正方形のらせんの外側へ物体を追加します。既存物体の transform は変わりません。object count は submit する instance 数であり、可視物体数を測定した値ではありません。カメラは固定しているため、N が大きいと画面端でのクリッピングや他の物体による遮蔽があります。CPU 側で視錐台カリングやオクルージョンカリングは行っていません。

1個の条件では、同じ小さな物体を1個だけ描きます。この1個の条件では draw 数を削減しません。短い処理時間では timer・driver・scheduler の揺れが差を占める可能性がある対照条件です。

計測方法と集計

CPU encode、queue submit、queue の完了を待つ blocking wait と、その合計を分けて記録したネイティブの実経過時間です。draw 数が減っても、GPU の処理負荷の削減や実機の高速化を意味するとは限りません。

encode の計測区間は、encoder の作成から render pass の記録、finish までです。submit は別の区間として計測し、その submission の queue 完了を待つ blocking wait も分けて記録します。この3区間の和が total です。llvmpipe は CPU で描画を実行し、submit 区間にも driver や実行処理が含まれる可能性があります。そのため、encode だけを全 CPU 負荷とは呼びません。command encoder や driver 内部のメモリ確保も、計測に含まれる可能性があります。readback、画像保存、固定の geometry/target/uniform の確保、pipeline の作成は計測に含めません。

各方式・repeat の前に 10 frame の warmup を行い、30 frame の計測を 3 repeat 実施します。視点は oblique→overhead、個数は 1→64→256→1024→4096 の順です。repeat 0 と 2 は individual→instanced、repeat 1 は instanced→individual の順に実行します。repeat 数が奇数なので、順序は完全には均等になりません。ランダム化、温度の統制、外部の CPU 負荷の統制は行っていません。

各条件90点を直接まとめて、通常の中央値と nearest-rank p95 を求めています。括弧内には、3 repeat それぞれの中央値の範囲を示します。90点は独立した実機実験90回ではなく、信頼区間や統計的有意差は推定していません。

行った実装

draw とデータ転送

初期化時に1組の geometry buffers を確保し、4096件 × 48 bytes ＝196608 bytes（192 KiB）の instance data を1度だけ upload します。個別 draw も同じ instance vertex buffer を使い、draw_indexed(0..36, 0, i..i+1) の first_instance で行を選びます。instanced は draw_indexed(0..36, 0, 0..N) を1回発行します。両方式とも scene pass は1回で、別の display pass で1 draw を実行します。

個別 draw ごとの uniform 書き込みや queue.write_buffer はありません。全方式・全 count で、毎 frame の instance upload は 0 bytes です。N を変えても、固定の 196608 bytes の buffer は確保し直しません。初期化時の upload 量と毎 frame の upload 量は区別します。動的シーンでの更新・コピー帯域は、今回の測定には含まれません。

考察と適用範囲

シーンの draw 数は N→1 になりますが、描くメッシュと三角形は同じ N 個分で、フラグメントの処理負荷も同じです。CPU encode の短縮は、記録した run についての結果です。それだけで処理全体の高速化を証明するものではありません。特に1個の条件では draw 数・instance 数が同じなので、その差は削減効果とは解釈しません。

GPU が処理の律速となるシーン、大きなフラグメント処理負荷、透明物の並べ替え、材質ごとの分割、動的な instance 更新は、別に検討する問題です。

ネイティブ実行は 1 scene と 1 display pass で構成します。camera uniform は初期化時に設定し、各 submit 後に完了を待ちます。Web の A/B 同時表示は、2 pane、毎 frame の uniform 更新、surface acquire/present、rAF、非同期 queue で構成されるため、条件が異なります。scene encoder の共有は描画経路の検証に役立ちますが、このネイティブの値を Web 版 A/B のフレーム時間とは呼びません。

ハードウェア GPU の timestamp、Android/desktop hardware、実ブラウザーでの WebGPU 操作や性能は、このネイティブ run では未確認です。専用 GPU での draw-call overhead、GPU utilization、overdraw、instance memory fetch の内訳は測っていません。

この証拠で確認したのは、静的な同一メッシュの描画コマンドをまとめる処理と、ネイティブ readback の一致です。実機で GPU timestamp と CPU のフレーム時間を分け、少数の物体、GPU が律速となる workload、複数の材質、毎 frame の instance 更新を別条件で検証してから、採用範囲を判断します。Android やブラウザーで一律に高速化するとは結論しません。

再現と証拠

再現コマンドと検査

Python 3.11 以上と Pillow が必要です。入力の相対パスはリポジトリのルートを基準にします。実測値の穴埋めや、既存の集計の再利用はしません。

RENDERING_LAB_INSTANCING_OUTPUT="$PWD/evidence/instancing" cargo test --locked --release -p rendering-core --test instancing_smoke -- --ignored --nocapture
python3 scripts/build-instancing-evidence.py --input evidence/instancing
python3 scripts/build-instancing-evidence.py --self-test
python3 scripts/build-instancing-evidence.py --check

生成スクリプトは20条件・60 repeat 群・1800点を検査します。検査対象は CSV header、sample 順序、重複・欠落、寸法、draw/pass 数、buffer と毎 frame の upload bytes、計測時間が有限かつ非負であることとその合計、カメラ・adapter・計測条件、画像寸法・RGB 形式・バイト一致です。

--check は本文・30 PNG・5 run files の36生成ファイルを一時領域で再生成し、バイト単位で比較します。PNG をバイト単位で再現するには、同じ Pillow/zlib 環境が必要です。source-snapshot は別記録のため、再生成・上書きはしません。

--self-test は、一時領域に明示的に作った人工 fixture だけを使います。正常入力、中央値/p95、欠落・重複・不明な条件・順序の違い・不正な寸法/draw/upload 量・非有限または負の計測時間・合計の不一致・metadata/image の不一致・出力の破損・余分なファイルを検査します。人工 fixture は、実測 evidence やレポートには保存しません。
