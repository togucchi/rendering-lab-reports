006 / Directional shadow mapping

結論と検証範囲

courtyard を変更しない別の実験として、1枚の directional depth map と、同じ indexed mesh を使う lit pass、共通の upsample を実装しました。以下は release native で画面外に描画して実際に読み戻した画像と、CPU wall time です。llvmpipe software rasterizer / OpenGL で得た結果であり、ハードウェア GPU の性能、GPU timestamp、ブラウザーや Android での実行を示す証拠ではありません。

固定したカメラ2条件 × 光源2条件で、既定値から map resolution、rasterizer constant bias、rasterizer slope bias、manual nearest-comparison PCF を一つずつ変えました。shadow-off の負荷比較用条件、再構成した深度、visibility のデバッグ表示を加えた48条件です。A/A 比較では、全静止画条件と全時間方向フレームで byte 単位まで完全一致しました。同じ single-pane Harness で繰り返した検証であり、runtime の独立した A/B slot target 同士を実行して比較した結果ではありません。

静止画では acne（表面の自己遮蔽模様）、contact detachment（接地点の隙間）、影の境界の階段状 aliasing を別々に見ます。bias を大きくすれば常に良くなるわけではありません。acne を減らす一方で接地を失うというトレードオフがあります。PCF は影の境界を平均するため、map resolution を増やした場合とは見え方が異なります。これは定性的な比較であり、正解画像に対する品質指標ではありません。

固定条件と範囲を限定した OFAT

  • 表示・内部解像度は 512×512、100%、t=0 で、MSAA は使いません。depth map だけを256/512/1024に変えます。既定値は512、constant preset1、slope preset1、PCF3×3です。
  • Constant presets0/1/2 は DepthBiasState.constant の0/2/65536、Slope presets0/1/2 は slope_scale の0/1/8に対応します。clamp0です。影を受ける側の比較には reference=light depth を使い、その側では depth/slope を減算しません。
  • Depth32Float の constant bias は、rasterizer の depth-format に依存する単位です。0/2/65536を normalized depth の0/.0005/.012と読み替えません。Slope は light-view の screen-space depth gradient に掛かります。
  • 光源へ向かう方向は、light0 が normalize([-0.6,1,0.5])、light1 が normalize([-1,0.3,0.35]) です。ortho extent±8、light eye=direction×20、near0.1/far40を使います。light0を high、light1を low と呼びます。
  • Camera0 は斜めから見た eye[8.2,6.8,10.5]、camera1 は真上から見た eye[0.1,17,0.1] です。target[0,0.6,0]、up[0,1,0]、45°の垂直 FOV、near0.1/far100、aspect1を使います。
  • 影の実験専用のジオメトリは 1,297vertices / 1,976triangles です。既存の courtyard に細い柱を3本と、傾斜した受影面を追加しました。元の courtyard mesh builder は変更していません。
  • On は indexed mesh の深度描画を1回、カラー描画を1回、全画面の upsample を1回行います。Off では depth pass を省略し、indexed mesh のカラー描画を1回、upsample を1回行います。Reconstructed depth は indexed mesh の深度描画を1回、全画面の depth-debug を1回（pixel ごとに16比較）、upsample を1回行います。Visibility は depth、indexed visibility、upsample の順に描画します。
  • PCF1/3/5 はそれぞれ1/9/25個の nearest comparison sampler の結果を明示的に平均します。textureSampleCompareLevel の offset 先を texel 中心に指定しているため、フィルタリングによる追加の比較 tap はありません。範囲外の tap は lit として扱います。

map resolution を変えると、サンプリング密度に加えて map の画素ごとの maxDepthSlope が変わります。そのため、slope_scale1 でも実効的な normalized/world-space bias が変わります。固定しているのは API パラメーターの値であり、実際に深度がずれる量ではありません。PCF も同じカーネル幅で覆う world-space の範囲が変わります。したがって、解像度による差を alias 密度だけの効果とは捉えません。

実画像からの観察と候補

既定の512/constant2/slope1/PCF3では、両方の光源で acne が残ります。high light の床・箱・球には密な縞があり、1024/PCF3では床に広がるモアレが目立ちます。解像度を上げただけで解決した結果ではありません。

constant0→2によって変化したのは、4通りの camera/light 条件で 5–19 / 262,144pixels だけです。違いはゼロではありませんが、この小幅な constant bias の変更では目立つ縞を解消しませんでした。

constant65536/PCF3は広い自己遮蔽の縞を減らしますが、細い柱の接触影も細く弱くします。slope8/PCF3では、さらに柱の根元に数 pixel の隙間が見え、球の接触影も大きく失われます。これらを普遍的な改善設定としては推奨しません。

今回の範囲に限った候補は512/constant2/slope1/PCF1です。今回の両方の光源では柱の根元と影の接続を保ち、PCF3で強かった広い表面縞がかなり減ります。ただし、影の境界は硬く階段状です。滑らかな影を求める用途の完成設定ではありません。UI の既定値は比較基準として残し、この候補を本番用の既定値とは呼びません。

切り抜き画像は、元の512×512画像の[85,250,355,390]を nearest で2倍に拡大しました。左が既定値、中央が constant65536、右が slope8です。フレームとジオメトリは同じで、輪郭を描き直していません。

Depth debug は、bias を適用した実際の light depth を、16回の nearest 比較による二分探索で再構成して灰色で表示します。値は約1/65536精度の量子化近似であり、厳密な float depth の読み出しではありません。白は far/no geometry を表し、距離 metres ではありません。Visibility は PCF の比較結果です。sRGB attachment を通すため、灰色の byte 値を linear visibility の数値そのものとは解釈しません。同じ光源であれば、depth-debug 画像は camera0/1で完全一致しました。

時間方向の比較と固定カメラ経路

world、light、object、map projection を固定し、24フレームで camera eye.x だけを8.2→8.9へ等間隔に動かします。camera target は固定しています。全条件に同じ f32 matrix を使い、各 frame の eye/target/column-major matrix を保存しました。これはカメラに追従する shadow-map stabilization のテストではありません。

以下は可逆圧縮の APNG です。生成時に100ms/frameを指定して再生しており、測定した FPS ではありません。描画した24フレームを0→23→22→1の46フレームで往復再生し、ループの端でカメラが急に飛ぶのを避けています。逆方向の部分は保存済みフレームの再生であり、追加の描画ではありません。描画した全フレームの PNG も保存しました。パレットの量子化や動画圧縮によるちらつきは加えていません。

左上は256/PCF1、右上は1024/PCF1、左下は256/PCF5、右下は1024/PCF5です。lit アニメーションの3行目左は shadow-off です。off でもカメラの移動によって物体の輪郭や表面が画素を覆う範囲は変わります。visibility アニメーションは影の比較を見やすくしていますが、受影面や物体の画面内での移動も残っています。

影の境界が不連続に移動したり、細い影が消えたりする箇所を、対応するフレームで比較します。連続フレーム間の単純な RGB 差には通常のカメラ移動も含まれるため、ちらつきのスコアとしては扱いません。このレポートでは時系列の画像を提示し、主観的な違いを見られる範囲にとどめます。acne/contact detachment の静的な比較と、移動時の境界の aliasing は別の現象です。一方を改善しただけで、他方も解決したとは主張しません。

保存した frame0/7/15/23の visibility 切り抜き画像では、256/PCF1で柱の影の長い斜辺に粗い段差が目立ち、1024/PCF1では段差が細かくなっています。ただし、1024でも画面の pixel 単位の raster alias は残ります。256/PCF5は境界を広く平均する一方、細い柱の影が薄くなり、白い受影面との区別がつきにくくなります。1024/PCF5はその影のコントラストを比較的保ちますが、細かい acne やモアレが画面上で動きます。フィルターを広げただけで時間方向のアーティファクトが消えたとは評価しません。

各行は256/PCF1、1024/PCF1、256/PCF5、1024/PCF5、各列は frame0/7/15/23です。[70,235,275,375]を切り抜き、nearest で2倍に拡大しました。off の比較用条件と画像全体で通常のカメラ移動を照らし合わせ、これらの変化を定量的なちらつきのスコアには変換しません。

Native release の wall time

各条件の各 repeat で3回のウォームアップ後に10サンプルを取得し、3回の繰り返しで1440サンプルを集めました。repeat0は全48条件を順方向、repeat1は逆方向、repeat2は24条件ずらした順序で実行しました。これは順序の影響を減らす限定的な釣り合わせであり、完全なランダム化や全順序の均衡ではありません。3回の繰り返しは同一プロセス内の区間であり、独立した3実験や信頼区間ではありません。

最終的に採用した run は、同時に動いていたビルド・レポート生成・テストのジョブを止めて取得しました。ただし、専用のハードウェアベンチマーク環境とは主張しません。

下表は各条件30サンプルをまとめて求めた通常の中央値と nearest-rank p95（ms）です。encode は encoder の作成、pass の記録、finish です。submit は queue.submit の呼び出し、wait はその submission が完了するまでの device.poll を測ります。total はこの3区間の和です。

9種類の depth variants と main・debug の pipeline 生成、リソース確保、uniform 更新、画像の読み戻し、アセット準備、surface acquire/present は測定時間に含めません。uniform 更新は runtime では frame ごとに発生します。

9種類の depth variants と main・debug をまとめて作成した API/validation の wall time は、一度の観測で11.127msでした。フレーム時間とは別のセットアップ負荷であり、ドライバーが後から行うコンパイル作業を完全に捉える保証はありません。

llvmpipe では描画自体が CPU 上で走り、submit/wait にドライバーの実行が含まれる場合があります。encode だけを全 CPU 負荷とは呼びません。off は depth draw と shadow sample loop の両方を除く比較用条件なので、差を depth-map pass 単体の負荷とは断定しません。

software adapter で PCF/map の時間が増減しても、ハードウェア GPU の順位や速度比には一般化しません。native の1ペイン直列 submit は、Web A/B の2ペイン、rAF、非同期 queue、画面表示とは条件が異なります。

Map 解像度と内部スケールの分離

シーンの内部 target を512→256→512へ切り替えても、同じ512²の shadow Map を保持し、Light.options.resolution は512のままです。元の解像度に戻した再構成深度の画像は、byte 単位で完全一致しました。50%表示では upsample と pixel sampling が異なるため、100%画像との一致は要求しません。

map のメモリー量は、Depth32Float の texel を格納する論理的な容量です。256²=262,144bytes、512²=1,048,576bytes、1024²=4,194,304bytesであり、ドライバーのオーバーヘッドや color/depth targets を含む総 VRAM ではありません。native harness は3サイズの map を事前に確保して保持し、条件ごとのメモリー確保を測定時間に含めません。

Backend 上の実際の制限と検証

  • Adapter: AdapterInfo { name: "llvmpipe (LLVM 19.1.7, 256 bits)", vendor: 65541, device: 0, device_type: Cpu, device_pci_bus_id: "", driver: "", driver_info: "4.5 (Core Profile) Mesa 25.0.7-2+deb13u1", backend: Gl, subgroup_min_size: 4, subgroup_max_size: 128, transient_saves_memory: None, limit_bucket: None }
  • 初回の native 作成は、GLSL backend が depth textureLoad に未対応だったため失敗しました。続けて試した noncomparison textureSampleLevel も、GLSL の sampler2DShadow signature で失敗しました。最終実装では nearest comparison sampler と texel 中心を指定する textureSampleCompareLevel を使い、離散的な比較を明示しています。depth debug だけは16比較の二分探索で深度を再構成します。同じ core API を runtime と test の双方で使います。成功した結果を Vulkan やハードウェアの結果に置き換えてはいません。
  • Native assertions では、静止画・時間方向の A/A byte 一致、on/off の差、両デバッグ画像が空ではないこと、clear 領域が白であることを確認します。正の raster bias で再構成深度が単調に増えること、不正な WGSL と誤った group ABI の拒否、カメラ間の再構成深度の一致、内部スケールを戻した後の一致も検証します。
  • Shader/pipeline を拒否するテストは、surface 上の live reload 操作や、ブラウザーの screenshot rollback を実行した証拠ではありません。WebGPU ブラウザー、ハードウェア GPU、Android、GPU timestamp は未検証です。

Issue #7の実験基準に対する証拠

  • Acne は、48条件の native 静止画読み戻し、visibility 表示、拡大した切り抜き画像を使い、基準と constant/slope/PCF を変更した結果を比較しました。
  • Floating/contact detachment は、constant65536・slope8での細い柱の根元と球の接触影を、同じ camera/light の切り抜き画像で比較しました。改善と引き換えに失われる影も明記しています。
  • Flicker/temporal aliasing では、light/world を固定した24フレームのカメラ経路、4通りの resolution/filter の組合せ、shadow-off の比較用条件、全 frame の PNG と可逆圧縮の APNG を保存しました。通常の移動と acne を分けて観察し、ちらつきの解消や定量的な品質スコアは主張しません。
  • 再現性と負荷については、固定メタデータ、3回×10サンプル×48条件の CSV、ウォームアップ・順序・clock の範囲、source/hash を保存しました。
  • 判断として、今回の範囲に限った硬い影の候補512/constant2/slope1/PCF1を記しました。PCF3/5の acne と、高 bias で接触影が失われるという失敗条件も記しています。

以上は Issue #7 の native 実験範囲の証拠です。ブラウザーとハードウェアは、別の Issue #1/#2 の未検証範囲として分け、この実験に新しいハードウェア要件は加えません。公開と Issue close の判断は別途行います。

base commit は非公開の PBR の4deccc8a3643a6115d7f62021fe7082b3730338eです。commit tree の全175ファイルが、レビュー済みの PBR snapshot と byte 単位で一致することを確認しました。base runtime/core snapshot inventory は、そのうち本実験前の runtime/core subset の hash を記録しています。presentation/report hotfix は subset の対象外です。測定記録を作成した時点では最終的な shadow source commit が未公開だったため、記録の値は null のままです。

native test は、実行 binary に埋め込んだ core/shader/test source を元の証拠に保存します。レポート生成器は、現在の source と一致することを要求します。その他の source と元の証拠の hash は source snapshot を参照します。

生成器は画像264枚+scale1枚+bias monotonicity2枚を検証します。CSV の順序・欠落・重複・有限値・合計、24フレームの経路、実行 source も確認します。--check は一時領域へ再生成して byte 単位で比較します。APNG・PNG の byte 再現には同一の Pillow/zlib 環境を使います。--self-test は実際の入力の一時コピーだけに不正値・欠落・順序変更を加え、それらが拒否されることを確認します。元の証拠には混ぜません。
