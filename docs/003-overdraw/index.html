RENDERING LAB実験と検証の記録

003 · 描画順序と depth prepass

depth prepass は heavy workload で back-to-front より改善しましたが、4条件すべてで並べ替え済みの front-to-back より遅い結果でした。一般的な最適化の推奨や、実機での高速化の保証にはしません。

実行環境は Mesa llvmpipe の CPU ソフトウェアラスタライザーで、backend は GL です。

目的と問い

同じ不透明なシーンの描画順序と depth prepass を変えたとき、画像とネイティブ実行の時間がどう変わるかを比較します。

比較条件

固定した条件

描画方式を比べる際は、同じ不透明な中庭を、同じ視点・フラグメント処理負荷・表示 512×512・内部 512×512（100%）・t=0 で描きました。

10個の不透明な物体を描き、頂点・インデックスバッファー、uniform、viewport、カリングは共通です。

adapter は llvmpipe (LLVM 19.1.7, 256 bits)、backend は Gl、device type は Cpu です。driver は (adapter API returned an empty driver name)、driver info は 4.5 (Core Profile) Mesa 25.0.7-2+deb13u1 です。

Rust のネイティブテストは unoptimized + debuginfo のプロファイルで実行しました。CPU encode/submit の数値にはデバッグ用テスト環境の影響も含むため、release WebAssembly の CPU 時間には外挿しません。

変えた条件

back-to-front、front-to-back、depth-prepass の3方式を比較し、2視点 × 2 workload × 3方式の12条件を測定しました。各 3 repeat × 30 sample、計1080点のネイティブ実行の実経過時間を記録しています。

oblique 視点の eye は [8.2, 6.8, 10.5]、overhead 視点は [0.1, 17, 0.1] です。両方とも target は [0, 0.6, 0]、world-up は [0, 1, 0] です。45° の透視投影を使い、near 0.1、far 100、t=0、viewport 512×512 に固定します。overhead には、真上の特異点を避けるための微小な横方向の offset があります。

計測方法と集計

以下の数値は、各 submit の完了を待つ直列実行の実経過時間です。GPU timestamp、フラグメントの実行回数、ブラウザーのフレーム時間、Android 実機の GPU 性能を示すものではありません。方式によって変わる draw/pass 数、CPU・driver のオーバーヘッド、queue の待機も含みます。そのため、時間差だけから early-Z の作動や削減量は断定しません。

各 frame で encode/finish/submit を行った後、その submission の queue 完了まで処理を止めて待ちます。cpu_encode_submit_ms、native_queue_wait_ms、その合計の native_queue_completion_wall_ms を別々に保存します。readback、画像保存、render target/buffer の確保、事前の物体の並べ替え、shader/pipeline の作成は計測に含めません。command encoder の作成や submit 内部でのメモリ確保は、計測に含まれる可能性があります。surface presentation、vsync、rAF は含みません。

1条件につき 1 scene viewport を使います。各 repeat・方式の前に 10 frame の warmup を実行し、その時間は CSV から除外します。測定は 30 frame × 3 repeat です。視点は oblique→overhead、workload は light→heavy の順に実行します。方式の順序は、repeat 0: BTF→FTF→prepass、repeat 1: FTF→prepass→BTF、repeat 2: prepass→BTF→FTF です。順序を循環させて固定順序の偏りを軽減していますが、ランダム化や CPU 負荷・温度の統制はしていません。開発中の再実行でも時間の変動が観察されたため、保存した最終 run の大小関係だけで安定した効果とは判断しません。

以下は、1条件90点をまとめた通常の中央値と nearest-rank p95 です。括弧内には、各 repeat の30点の中央値について最小〜最大を示します。pooled 中央値は3つの中央値の中央値ではなく、90点を直接並べた中央2値の平均です。独立した実機実験90回を意味するものではなく、統計的有意差や信頼区間は推定していません。

行った実装

描画順序とパス

back-to-front / front-to-back は、物体の AABB 中心をカメラの前方へ射影した深度を使い、それぞれ逆順・正順に並べ替えます。物体の範囲が重なるため、三角形単位・画素単位の完全な奥行き順序は保証しません。

通常方式は depth compare を Less に設定し、深度の書き込みを有効にします。depth-prepass では fragment stage と color attachment を使わず、同じ頂点計算と geometry で描画し、Less で深度を書き込みます。続く color pass ではその深度を Load し、Equal と深度書き込み無効の設定で、同じ順序の geometry を再描画します。prepass の draw 順は front-to-back です。

light/heavy の両 WGSL では builtin vertex position に @invariant を指定し、別の pipeline でも同じ頂点計算による深度の一致を保ちます。custom WGSL で Equal prepass を使う場合も、両 pass で一致する頂点処理と @invariant position が必要です。透明物、alpha test、discard、fragment depth 出力は扱いません。

全方式で内部の Rgba8UnormSrgb color と Depth32Float を使います。100% でも共通の fullscreen triangle 1 draw / 1 pass で表示へ転送します。linear-light bilinear clamp sampling の後、表示の sRGB attachment へ encode します。シーン以外のこの 1 draw / 1 pass も実経過時間に含めます。

フラグメント処理の負荷

light には通常の Lambert shader を使います。heavy では形状と頂点計算を保ったまま、補間された world position/time に依存し、出力色に寄与する64回の sin/cos 逐次計算をフラグメント処理に加えます。最適化後の命令数やフラグメントの実行回数は測定していません。

今回の差は最大 4 pixels に限られます。交差する面や共有辺の付近で深度が同値になることや、ラスタライズ精度による差と整合しますが、実機の pixel history で原因を確定したわけではありません。方式をまたいだ bit-exact 一致は合格条件にしていません。

固定 512×512 での回帰検証の許容値は、MAE<0.001、変化した pixel 数≤8、最大 channel 差≤40 です。この閾値は今回のシーン専用であり、一般的な知覚品質を保証しません。全画像で平均した MAE では、局所的な差が小さく表れます。

追加の回帰検証

ネイティブテストでは、この12条件に加え、内部 75%/50% でも 2視点 × 2 workload × 3方式の24 readback を回帰確認しました。追加条件は1080点の計測条件には混ぜていません。このレポートの画像と集計は、すべて内部 100% の結果です。

考察と適用範囲

この実行での大小関係は上の数値のとおりです。すべての視点・workload に共通する最適な方式を示すものではありません。特に prepass は、シーンの draw 数を 10→20、pass 数を 1→2 に増やします。heavy はフラグメント側の計算を増やした人工的な負荷なので、時間差があっても overdraw だけに原因を限定できません。専用 GPU やタイルベースのモバイル GPU では、結果が変わる可能性があります。

ネイティブのベンチマークは、1枚の 512×512 シーンと 1 draw の composite pass で構成します。uniform は初期化時だけ設定し、queue の完了を直列に待ちます。実際の Web 版は 2 pane と共通の composite pass 内の 2 draw で構成し、毎 frame の uniform 書き込みと surface acquire/present を行います。完了待ちは行いません。scene encoder の共有は描画経路の確認に役立ちますが、ネイティブの数値を Web 版の A/B 同時実行の時間としては扱えません。

ハードウェア GPU の timestamp query、pipeline statistics、fragment invocation、overdraw counter、pixel history は取得していません。このレポートから実際のフラグメント削減数や early-Z の効率は算出しません。

この証拠で確認したのは、共有 renderer を使ったネイティブのオフスクリーン描画、許容範囲内の画像差、直列実行の実経過時間です。WebGPU surface、ブラウザーでの A/B 同時表示や操作、Android 端末の新モード・実機性能は、この実行では確認していません。Issue #4 の完了条件は、この固定シーン・ネイティブの llvmpipe 実験の範囲で満たしました。実ブラウザー・ハードウェア GPU の検証は、Issue #1/#2 と今後の追試に残ります。

再現と証拠

再現コマンドと検査

ネイティブ実行の出力先は絶対パスで指定します。Python 3.11 以上と Pillow で画像・集計・本文を再生成できます。入力の相対パスはリポジトリのルートが基準です。既存の集計を再利用したり、架空の計測値で補完したりはしません。

RENDERING_LAB_OVERDRAW_OUTPUT="$PWD/evidence/overdraw" cargo test --locked -p rendering-core --test overdraw_smoke -- --ignored --nocapture
python3 scripts/build-overdraw-evidence.py --input evidence/overdraw
python3 scripts/build-overdraw-evidence.py --self-test
python3 scripts/build-overdraw-evidence.py --check
python3 scripts/build-reports.py
python3 scripts/build-reports.py --check

生成スクリプトは12条件・36 repeat 群・1080点を検証してから出力します。検査対象は、CSV header、sample 順序、重複・欠落、寸法、draw/pass 数、計測時間が有限かつ非負であることとその合計、カメラ・計測条件、画像寸法・RGB 形式・MAE・局所差の閾値です。3つの計測時間それぞれについて、通常の中央値と nearest-rank p95 を6桁に丸めて集計します。

--check は一時領域で再生成し、本文・16 PNG・5 run files の22ファイルをバイト単位で比較します。別途記録する source-snapshot.json は形式だけ確認し、生成・上書きはしません。PNG をバイト単位で再現するには、同じ Pillow/zlib 環境が必要です。

--self-test は、一時領域に明示的に作った人工 fixture だけを使います。正常入力の再現性、偶数点の中央値、p95 を確認します。また、欠落・重複・不明な条件・不正な寸法・draw/pass 数・非有限または負の計測時間・合計の不一致・順序の違い・metadata/image の不一致・壊れた出力・余分なファイルを拒否します。人工 fixture を実測レポートとして保存しません。
