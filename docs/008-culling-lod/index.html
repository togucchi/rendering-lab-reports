RENDERING LAB実験と検証の記録

008 · CPU frustum culling + distance LOD

同じ中庭・seed0・camera path・時刻・512×512・material・固定lightで、最高detail/no culling、cullingのみ、LODのみ、両方を比較します。実装はWeb/native共通。以下の画像・数値はnative release / llvmpipe software CPU / GLの実readbackです。実browser・hardware GPU・Android・GPU timestampは未検証です。

結論と範囲

  • 81時刻×4方式の324画像。culling-onlyは同時刻のhighest-detail baselineと全pixel一致。bothは同時刻のLOD-onlyと全pixel一致。これは試した経路・解像度で誤った欠落がなかった証拠で、全入力の保証ではありません。
  • LODは実際に別のindex/vertex meshへ切替。12/24 world unitsで1840→440→100 triangles/sphere。床・箱はdetailを変えません。51objects中41がmulti-detailです。
  • cullingは画面外候補を省きます。壁や前景に隠れた物体もfrustum内なら描画します。occlusion cullingではありません。
  • 独立したA/B設定・uniform・target・draw selection、逆順/再描画一致、invalid WGSL/ABI拒否、custom shader復元をnative harnessで検証。surface/DOM end-to-endと同一視しません。
  • 下記の限定的な画像誤差目安（MAE≤0.5 byteかつchannel差>8のpixels≤1%）を満たさなかったframe: なし。最大whole-frame MAEは0.2551 byte。細い輪郭の局所差やthreshold往復のちらつきが小さいという保証ではありません。

Scene、境界と判断コスト

元の床・囲い・箱・中央球を維持し、外側groundと40個の回転/nonuniform-scale ellipsoidを追加。固定配置で入力乱数はありません。各LODのgeometryは起動時にworld-spaceへ変換し、一度だけuploadします。法線はinverse-transpose相当（scaleで割ってY回転）で正規化。boundsはlocal AABBの8cornerをworld変換しmin/maxを取り、全LOD共通の保守的なboxを使います。全objectsとranges。

column-major VPからleft/right/bottom/top/near/farの6planeを抽出し正規化。WebGPUのnearはrow2、farはrow3-row2。AABBのpositive vertexがplaneの外側に0.0001 world unitsより遠い場合だけ棄却。接触・交差は残し、nonfinite camera planeはfail-open。CPU frustum phaseにはplane抽出・51bounds判定・visibility flags構築を含みます。baseline/LOD-onlyの同phaseは全true flags作成のみです。

LOD距離はeyeからtransformed AABB centerまでのEuclidean distance。distance<12はhigh、12≤distance<24はmedium、24≤distanceはlow。ちょうど境界ではlower detail。履歴・hysteresis・crossfadeなし。同時刻へseekしても同じ結果。CPU LOD/selection phaseには距離判定と安定順draw list構築を含みます。56,595vertices×36bytes＋293,070indices×4bytes=3,209,700bytes（約3.06MiB）の静的geometryを全方式・A/Bで共有します。全LODを保持し、Core起動時に他の実験を選んでいてもuploadします。alignment/driver/既存実験のallocationは除外。LODはこの実装のbuffer容量を減らしません。one object = one draw batchで、棄却したbatchのみdrawを省きます。別実験issue5のinstancingは変更・合成していません。

同経路とpop / flicker

20秒clamped pathを0.25秒刻みで81frame保存。最初は斜め→近接→左edge sweep、その後cameraは中心球から10→26→10 unitsへ往復し12/24の両境界を跨ぎます。最後4秒は中心球の12±0.04unitsを繰り返し跨ぎます。timeはcameraだけを変更しlight/sceneは固定。coreはpath終端より後の入力で最後のcameraを保持。Web再生は20秒でloopします。A/B比較は50:50と同じ内部倍率で行います。Camera path。

中心cropは512²画像のx/y176..336をnearest拡大。上が同時刻high、中央がLOD、下がabs差分8倍。12±0.04unitsの往復はhard boundaryの挙動を意図的に露出します。静止距離での繰り返しreadbackは一致する一方、境界を跨ぐcamera揺れではhigh/mediumが往復するためpop/flickerを完全には避けられません。画像誤差目安内の中遠景の検証用としては候補ですが、安定した本番cameraにはhysteresisまたはcrossfadeと実機/実表示サイズの確認が必要です。LODを「見た目が同じ」とは判定しません。

全frame差分には同時刻baselineとの差と、連続frameのsigned(LOD-baseline) residual変化を保存。後者はcamera移動由来のbaseline変化を差し引く補助指標であり、知覚的なflicker量ではありません。324画像のinventory。

反復CPU計測

8時刻×4方式×3repeat×10samples=960samples、各block4warmups。mode順をrepeat毎に入替。初回geometry/pipeline準備とreadbackは計測外。cpu_encodeにはuniform write/command generation/scene pass/100%同寸upsample/finishを含み、frustumとLOD list構築は別列。1scene pass +1upsample pass、scene draw=visible objects、upsample draw=1。全方式とも同じ表示経路です。

native completion wallにはCPU決定・encode・submit・queue待ちを含みます。native_frame_intervalは同block内で実測したstart-to-start、各block最初は空欄。VSync/rAF間隔やGPU timestampではありません。GPU msは空欄。小さなsceneではculling判断の固定コストが利得を上回り得ます。CPU software rasterizerでのtriangle削減効果をhardware速度向上率に読み替えないでください。

t=0では51→22draw、75,550→22,190triangles(cull)、両方では2,330triangles。frustum判断の中央値は約1µsで0costではありません。t=10ではculling-onlyのpooled completion6.047msがbaseline5.088msより遅く、t=4bothのrepeat中央値は1.882–8.548msに広がりました。この実行ではCPU/driver負荷の揺れが大きく、両方が常に速いという結論は出しません。幾何count削減と表示誤差は再現した一方、性能候補は実機で反復確認が必要です。
